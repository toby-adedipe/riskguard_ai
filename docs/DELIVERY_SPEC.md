# Layer 6 — delivery spec (evidence, decisions, audit, filing)

_Part of the demo→product bundle. This is where the system's conclusions become artifacts humans and regulators act on: the evidence pack, the consumer notice, the human approval gate, the append-only audit, and the regulator filing. It consumes layer 4 (validated agent output) and layer 5 (the rulepack), and it is the layer the buyer actually sees._

## 0. What "as real as possible" means here

For the demo, delivery produces **genuine, recognizable artifacts**, not mockups:
- A real PDF evidence pack a compliance officer would accept as a first draft, with a content hash and the rulepack version stamped on it.
- A real consumer-notice draft in the exact fields the rulepack requires.
- A working human-approval gate that gates recovery and writes an immutable audit entry.
- A real audit log with hash-chained integrity.

The **only** mocked boundary: we generate the NCC Uptime portal *submission payload* and let a human file it — we do not auto-submit to the live regulator in the demo. Everything up to "click submit" is real.

## 1. The evidence pack

Builds on the existing `NCCPack` schema (`app/modules/compliance/schemas.py`) — 7 sections already defined: `timeline`, `affected_services`, `kpis`, `impacted_subscribers`, `root_cause`, `corrective_actions`, `approval_history`, `evidence_logs`. Today `ComplianceService.build_pack` returns them mostly empty. Delivery fills them **for real, from provenance-controlled sources**.

### 1.1 Provenance rule (non-negotiable)
Every line in the pack traces to a source of record. Nothing is authored free-hand by the assembler:

| Section | Filled from | Rule |
|---|---|---|
| `timeline` | incident record (open/phase transitions) + audit entries + validated agent notes | UTC, ISO 8601, ordered; each entry cites its source id |
| `affected_services` | detection blast radius + topology | derived, not asserted |
| `kpis` | `FeatureWindow`/`SignalEvidence` at incident peak | actual readings with baselines |
| `impacted_subscribers` | impact-exposure agent output (validated) | exactly the validated number — no re-derivation |
| `root_cause` | network-forensics agent (validated) | **hedge-preserving** — "evidence indicates a probable X", never hardened to "X occurred" |
| `corrective_actions` | approved mitigations in the audit trail | only approved/executed actions; proposed-but-unapproved are marked as such |
| `evidence_logs` | evidence store ids + agent tool-call trace | the audit spine of the whole conclusion |

Extend `NCCPack` with three fields the current shape lacks: `status` (`draft` \| `final`), `rulepack_version` (from layer 5), and `content_hash`. A pack is `draft` until a compliance officer marks it `final`; the hash is computed at `final` and recorded in the audit log.

### 1.2 Completeness honesty
A pack assembled before the investigation converges shows **explicit gaps** ("Root cause: investigation in progress — leading hypothesis: probable transport break, confidence 0.72") rather than blanks or padding. A visibly-incomplete draft is compliant work-in-progress; a padded one is a liability. The compliance agent (layer 4) owns the wording; delivery owns the assembly and the gap-marking.

### 1.3 Rendering
Two renders from one `NCCPack`: a **PDF** (human/regulator-readable, letterhead, sections, evidence appendix) and a **structured JSON** (the Uptime-portal payload shape). Both carry the hash + rulepack version + generation timestamp. The signature line follows the pattern already sketched in `docs/COMPLIANCE_DOCUMENTATION.md` but the hash must be a real digest of the content, not a decorative string.

## 2. The consumer notice

A separate artifact from the regulator pack, governed by the rulepack's `consumer_notice` section. Fields: cause (hedged to evidence), affected areas, expected restoration time (only if a grounded estimate exists, else "to be advised"). Draft is generated by the compliance agent, held in `draft` state, and **requires human approval before any send** — same gate as actions (§3). Prohibited content (liability admissions, unbacked restoration promises, jargon, subscriber PII) is enforced both in the agent prompt and by a delivery-side lint that rejects a notice containing an MSISDN pattern or an un-approved restoration time.

## 3. The human approval gate

The only path from recommendation to action. Builds on the existing `actions` module (`ActionSimulateRequest/Response`, `ActionApproveRequest/Response`, `ActionProjection`) — `approve()` already writes an audit entry correctly; `simulate()` is the stub to make real.

Flow:
```
mitigation-planner agent proposes options (requires_approval: true, always)
  → ActionController.simulate(incident, action_ids) → real projected curves vs do-nothing
     (calls engine.run_pre_action_simulation — deterministic projection, not the agent)
  → operator sees: recommended option, do-nothing baseline, side effects, reversibility
  → operator approves ONE option (RBAC: only an authorized operator role may approve)
  → ApprovalService: append AuditLogEntry (operator, action, expected_impact, rationale, ts)
  → this audit entry is the ONLY trigger that moves the incident to MITIGATING / recovery
  → detection lifecycle (layer 3) observes the approval and transitions phase
```

Rules: no agent and no automation may approve; the operator identity comes from auth (not a stubbed `/me`); an approval is immutable once written; approving requires the operator to have *seen* the simulation (the UI enforces it, the audit entry references the simulation id). This gate is the answer to "is it autonomous / safe?" — the reasoning is autonomous, the *acting* is never.

## 4. The audit log

Extends the existing append-only `AuditLogRepository`. It is a **compliance artifact**, not debug output. What gets logged, each as an immutable entry:
- incident opened / phase transitions (from detection)
- each agent investigation: start, tool calls, final validated output, validator verdict
- each simulation run
- each human approval (already implemented)
- each pack generation + finalization (with hash)
- each consumer-notice approval + send
- each regulator submission (payload + timestamp + who filed)

Integrity: **hash-chain** the entries (each entry includes the hash of the prior) so the log is tamper-evident — a regulator or auditor can verify no entry was altered or removed after the fact. Export as a signed bundle. Retention per tenant/regulator config. No edit, no delete, ever — enforced at the repository, which already documents this ("Append-only audit log. Never edit, never delete.").

## 5. Regulator filing

- **Format**: the structured-JSON render of the `final` `NCCPack`, shaped to the NCC Uptime portal payload (schema to be confirmed — see rulepack `verification`).
- **Demo boundary**: generate the payload + PDF, present a "review & file" screen, log the *intent* to file; a human clicks submit against the real portal outside the system. We do **not** auto-submit to a live regulator in the demo (and probably not in early production — filing to a regulator is a human-accountable act).
- **Deadline tracking**: the rulepack `reporting` obligations drive countdown timers surfaced on the dashboard (§6); a breach of a reporting deadline is itself an audited event.

## 6. The dashboard (delivery to humans)

The UI is part of delivery — it is where a non-engineer experiences the whole system. Minimum surfaces for the demo, all consuming existing/near-existing endpoints:
- **Live incident + risk map** (`/risk/map`, `/incidents/{id}`) — the unprompted detection.
- **Investigation view** — the agent reasoning trace as it happens: hypotheses considered, tools called, findings, the critic's verdict. This live reasoning trail is the demo's signature moment (no dashboard vendor can fake it) — surface it, don't bury it.
- **Decision panel** — simulated options vs do-nothing, the approval gate (§3).
- **Compliance panel** — classification + clause citation, deadline countdowns, the draft pack and consumer notice, the "review & file" screen.
- **Audit view** — the hash-chained timeline, exportable.

Design note: the dashboard renders only what the API returns (the existing frontend boundary — no client-side computation). Delivery's job is to make sure the API returns real, provenance-stamped content for each panel.

## 7. Definition of done (layer 6)

- A converged investigation produces a `final` `NCCPack` with all 7 sections populated from provenance-controlled sources, a real content hash, and the rulepack version stamped.
- Root-cause and consumer-notice wording preserve the agents' hedges (no certainty inflation between layer 4 and the filed artifact).
- Recovery cannot start without a human approval that references a simulation; the approval is an immutable, hash-chained audit entry.
- The audit log verifies (hash chain intact) and exports as a signed bundle.
- The Uptime payload and PDF generate; the "file" action is human-gated and audited.
- Kill the LLM provider: delivery still produces a deterministic pack (detection + rulepack + engine numbers) marked "analysis unavailable — deterministic outputs only." Delivery never depends on the agents being up.
